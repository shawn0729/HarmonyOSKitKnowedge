# fix-issue — GitHub Issue Driven Fix Workflow

## Command Variants

| Command | Action |
|---------|--------|
| `/fix-issue <N>` | Fix an issue (auto-detects first fix vs continued fix) |
| `/fix-issue close <N>` | Close issue after verification + log experience |
| `/fix-issue list [--mine]` | List all (or only my) open bug issues |
| `/fix-issue triage [--mine]` | Priority-sort all (or only my) open issues |
| `/fix-issue auto [--mine]` | Batch fix all (or only my) open bug issues sequentially |

---

## `/fix-issue <N>` — Unified Fix Flow

### Step 1: Prerequisites Check

```bash
gh auth status
git status --short
```

**Abort if:**
- gh CLI not authenticated
- Working tree has uncommitted changes (tell user to commit/stash first)

### Step 2: Fetch Issue

```bash
gh issue view <N> --repo fuxi-ailabs/antennapod_arkts --json number,title,body,labels,state,assignees,comments
```

- If issue doesn't exist → report and stop
- If issue is closed → "Issue #N is already closed. No action needed." and stop

### Step 3: Detect Mode (First Fix vs Continued Fix)

Check two conditions:
1. Does branch `fix/issue-<N>` (or `feat/issue-<N>`) exist on remote?
2. Do the issue comments contain a prior reply with "Generated by Claude Code `/fix-issue`"?

```bash
git ls-remote --heads origin fix/issue-<N>
```

| Branch exists? | Prior reply exists? | Mode |
|---|---|---|
| No | No | **First Fix** → go to Step 4A |
| Yes | Yes | **Continued Fix** → go to Step 4B |
| Yes | No | **Continued Fix** (branch was created but reply failed) → go to Step 4B |
| No | Yes | **Continued Fix** (branch was merged) → create new branch from main, go to Step 4B |

### Step 4A: First Fix Flow

#### 4A.1: Parse Structured Fields

Issue body is generated by GitHub Issue Template. Split by `### ` headers to extract:

**Bug Report fields:**

| Header in body | Variable | Purpose |
|---|---|---|
| `### Page Location` | page_location | Locate source files |
| `### Bug Category` | bug_category | Choose fix strategy + Skill |
| `### Actual Behavior` | actual_behavior | Understand the problem |
| `### Expected Behavior` | expected_behavior | Define fix target |
| `### Steps to Reproduce` | repro_steps | Understand trigger path |
| `### Screenshots / Screen Recording` | screenshots | Visual reference |
| `### Android Reference Screenshot` | android_ref | Android comparison |
| `### Error Log` | error_log | Technical clues |
| `### Device Type` | device_type | Environment factor |
| `### API Version` | api_version | Compatibility factor |
| `### Additional Context` | additional_context | Extra clues |

**Feature Request fields:**

| Header in body | Variable |
|---|---|
| `### Feature Area` | feature_area |
| `### Suggested Priority` | priority |
| `### User Story` | user_story |
| `### Proposed Solution` | proposed_solution |
| `### Android Reference` | android_reference |
| `### Design Mockup` | design_mockup |

**Issue type detection:**
- Label `bug` → Bug Report
- Label `enhancement` → Feature Request
- Neither → infer from title prefix `[Bug]` or `[Feature]`

Skip fields with `_No response_` value.

#### 4A.3: Analyze & Fix (Using Skills + Spec)

**MUST do all three before writing any fix:**

**a. Consult spec-index.md + baseline/L2-migration.md**

Read `spec/spec-index.md` 找到主索引，再读 `spec/baseline/L2-migration.md` to find the relevant SS chapter:

| Bug Category | Spec Chapter |
|---|---|
| UI display issue | SS4 (UI Mapping) |
| Feature not working | SS3 (Tech Stack Replacement) |
| Crash / Force close | SS3 + dev-pitfalls |
| Data loss / Inconsistency | SS5 (Data Model) |
| Playback issue | SS3 Solution 10 (AVPlayer) |
| Download issue | SS3 Solution 1 (HTTP) |
| Navigation / Routing | SS4 (Navigation Architecture) |
| Performance issue | SS4 (Adapter → LazyForEach Mapping) |

**b. Check dev-pitfalls.md**

Read `docs/dev-pitfalls.md` to check if this bug hits a known pitfall. Also check CLAUDE.md Top-10 table.

**c. Invoke the appropriate ArkTS Skill**

| Bug Category | Primary Skill | Secondary Skill |
|---|---|---|
| UI display issue | `arkts-component-builder` | `arkts-ui-alignment` |
| Feature not working | `arkts-knowledge-verifier` → routes to specific Skill | — |
| Crash / Force close | `arkts-knowledge-verifier` | `arkts-system-capabilities` |
| Data loss / Inconsistency | `arkts-data-layer` | — |
| Playback issue | `arkts-media-playback` | — |
| Download issue | `arkts-download-manager` | — |
| Navigation / Routing | `arkts-navigation-builder` | `arkts-state-manager` |
| Performance issue | `arkts-component-builder` | `arkts-pattern-library` |

**d. Apply fix** following ALL rules in `CLAUDE.md`:
- No `any` type
- No `as` assertions
- Kit unified imports
- SQL `?` placeholders
- `ResultSet` must be closed
- NavDestination params in `onReady`, not `aboutToAppear`


### Step 4B: Continued Fix Flow

#### 4B.1: Check for New Feedback

Read issue comments. Find comments posted AFTER the last "Generated by Claude Code `/fix-issue`" reply.

**Stop if** no new comments found → "No new feedback on issue #N since last fix. Nothing to do."

Extract from new comments:
- New problem description
- New screenshots (if any)
- Additional repro steps or error logs

#### 4B.2: Switch to Fix Branch

```bash
git fetch origin
git checkout fix/issue-<N>
git pull origin fix/issue-<N>
```

If branch doesn't exist (already merged), create from latest main:

```bash
git checkout main
git pull origin main
git checkout -b fix/issue-<N>
```

#### 4B.3: Analyze & Fix

Same as 4A.3 (consult Spec + dev-pitfalls + invoke Skills), but:
- Focus on the **new feedback** specifically
- Read the previous fix to understand what was already changed
- Avoid reverting previous fixes unless they caused the new issue

#### 4B.4: Commit & Push

```bash
git add <changed files>
git commit -m "$(cat <<'EOF'
fix: <description of continued fix> (#<N>)

Address feedback from issue #<N>:
- <what was additionally fixed>

Fixes #<N>

Co-Authored-By: Claude Opus 4.6 (1M context) <noreply@anthropic.com>
EOF
)"
git push origin fix/issue-<N>
```

→ Continue to **Step 5: Reply to Issue**

## `/fix-issue list [--mine]`

Without `--mine`: list all open bug issues.
With `--mine`: list only issues assigned to the current user.

```bash
# All open bugs
gh issue list --repo fuxi-ailabs/antennapod_arkts --state open --label bug --json number,title,labels,assignees,createdAt --jq '.[] | "#\(.number) \(.title) [assigned: \(.assignees | map(.login) | join(","))] [\(.createdAt | split("T")[0])]"'

# Only my issues (--mine)
gh issue list --repo fuxi-ailabs/antennapod_arkts --state open --label bug --assignee @me --json number,title,labels,createdAt --jq '.[] | "#\(.number) \(.title) [\(.createdAt | split("T")[0])]"'
```

## `/fix-issue auto [--mine]` — Batch Fix Flow

Automatically iterate through all open bug issues and fix them one by one.

- Without `--mine`: fix all open bug issues.
- With `--mine`: fix only issues assigned to the current user (`@me`).

### Step 1: Collect Issues

```bash
# Without --mine
gh issue list --repo fuxi-ailabs/antennapod_arkts --state open --label bug --json number,title,assignees,createdAt --jq '.[] | .number' | sort -n

# With --mine
gh issue list --repo fuxi-ailabs/antennapod_arkts --state open --label bug --assignee @me --json number,title,createdAt --jq '.[] | .number' | sort -n
```

If no issues found → "No open bug issues to fix." and stop.

### Step 2: Display Plan

Output a summary table before starting:

```
Found <count> open bug issue(s) to process:
| # | Issue | Title | Assignee |
|---|-------|-------|----------|
| 1 | #<N1> | <title1> | <assignee1> |
| 2 | #<N2> | <title2> | <assignee2> |
...

Starting batch fix...
```

### Step 3: Iterate and Fix

For each issue in the list, sequentially:

1. **Fetch issue details** — same as `/fix-issue <N>` Step 2
2. **Skip if closed** — "Issue #N is already closed. Skipping."
3. **Detect mode** — same as `/fix-issue <N>` Step 3
4. **If First Fix** → execute Step 4A (full fix + branch + PR + reply)
5. **If Continued Fix** → check for new feedback:
    - **Has new feedback** → execute Step 4B (continued fix + push + reply)
    - **No new feedback** → "No new feedback on issue #N. Skipping."
6. **Return to main branch** before proceeding to the next issue:
   ```bash
   git checkout main
   git pull origin main
   ```

### Step 4: Summary Report

After all issues are processed, output a final summary:

```
## Batch Fix Complete

| Issue | Status | Action |
|-------|--------|--------|
| #<N1> | ✅ Fixed | PR #<PR> created |
| #<N2> | ⏭️ Skipped | No new feedback |
| #<N3> | ✅ Fixed | Continued fix pushed |
| #<N4> | ⏭️ Skipped | Already closed |
...

Fixed: <X> | Skipped: <Y> | Total: <Z>
```

### Error Handling

- If a fix fails for one issue (e.g., merge conflict, compilation error), log the error and continue to the next issue:
  ```
  | #<N> | ❌ Error | <error description> |
  ```
- At the end, list all errored issues so the user can address them manually.
